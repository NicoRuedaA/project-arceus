# Field object placements (resident_release.gfpak)

Status: partially decoded. Sheet [`data/field_object_placements.tsv`](../../data/field_object_placements.tsv), regenerated by
`.tools/placement_decode.py` (needs `.tools/gfdump` and the game's `resident_release.gfpak`). Terrain cross-check:
`crates/pla/examples/placement_terrain_check.rs`. Nothing here is a runtime-behaviour claim.

## Where the placements are
`bin/archive/field/resident_release.gfpak` (2,066 entries) stores no names, only FNV-1a 64 of each full path. One entry
(index 2042, 212 KB) is a FlatBuffers path manifest that lists 2,290 `bin/...` strings; 1,811 of them hash to an entry of the pack
(479 are listed but not shipped in it). Of those, 1,784 are `bin/field/param/placement/<area>/<kind>/...` files. Objects
(buildings, props, fences, rocks, fields, signs) are in `<kind> = bg_parts`; the other kinds were located but not decoded.

Files present in the pack (non-empty = more than 24 bytes), by kind and area. Every kind has the same area set: `ha_area00`
(+31 subareas), `ha_area01`..`05`, `ha_area06`, `ha_area11` and subareas; main areas are the large files.

## Format (bg_parts.bin, FlatBuffers, field numbers only)
| Field | Meaning | Confidence |
|---|---|---|
| root.f0 | vector of objects | high |
| object.f0 | key string (e.g. `none`, `bg_parts_cellphone`, a scene label) | high (string), meaning medium |
| object.f2 | u64 = FNV-1a 64 of the **model name** (e.g. `objects_area00_house17_b`) | high: 2,467/2,467 resolve to a known name |
| object.f1 | u64 object-group id | medium (unique, meaning unknown) |
| object.f4 | vector of instances | high |
| instance.f7 | position x,y,z (floats, metres, area-local) | high: heights match the terrain (below) |
| instance.f8 | rotation x,y,z, likely degrees (seen 0, 90, 180, -90, 178.9); missing field = 0 | medium |
| instance.f9 | scale x,y,z (default 1) | medium-high |
| instance.f2..f6 | strings: event/system flag names and values (`FSYS_UPDATE_VILLAGE_6`, `WSYS_FARM_UPDATE_COUNT`...) | strings high, meaning unknown |
| instance.f0/f1 | u64 ids | unknown |

Rotation axis order and the Euler convention (apply order) are not verified.

## Cross-check against the terrain heightmap
`placement_terrain_check` compares placement y with `TerrainArea::sample_world_height` of the same area (extent 1025x1025):

| Data | Placements | Inside extent | Mean abs dy | Within 3 units |
|---|--:|--:|--:|--:|
| ha_area00 main | 249 | 248 | 0.93 | 96.4 % |
| ha_area01 main | 487 | 486 | 2.36 | 89.5 % |
| ha_area02 main | 502 | 501 | 1.45 | 97.6 % |
| ha_area03 main | 124 | 123 | 4.59 | 85.5 % |
| ha_area04 main | 438 | 437 | 2.69 | 95.9 % |
| ha_area05 main | 391 | 390 | 1.27 | 93.9 % |
| ha_area00 subareas | 80 | 79 | 2.59 | 73.8 % |
| ha_area01..05 subareas | 160 | 160 | 32-235 | 0 % |

Main-area placements sit on the terrain. Subareas of areas 01-05 (caves, interiors, camps) use their own local frames, so their y
does not follow the open-world heightmap; do not place them on the main terrain. Their frame (and the ha_area00 subareas that
fail the height test) is unknown.
