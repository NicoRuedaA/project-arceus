# Installer: from the user's own dumps to a ready `./play.sh` (Brief 40)

`./install.sh --base <pk1.nsz> --update <pk2.nsz> --keys <prod.keys>` (code in
[`.tools/setup_cache.py`](../../.tools/setup_cache.py), safe writes in
[`.tools/safe_io.py`](../../.tools/safe_io.py)) checks the user's files, extracts the
base + update data folder and builds every cache the viewer reads, each step only when its
output is missing or stale. `./install.sh --check` changes nothing and prints the exact
commands. `./play.sh` runs a read-only pre-flight first. Player guide:
[`docs/INSTALL.md`](../../docs/INSTALL.md) / [`docs/INSTALL.es.md`](../../docs/INSTALL.es.md).

## Cache dependency map (measured)

One run on the maintainer's machine, 2026-10-13, into a throw-away folder
(`work/e2e` of the `install` worktree), memory limit 6 GB per command, 3 build jobs, other
agents working on the same disk at the same time.

Generated by the viewer itself at run time, so not an install step: the effect textures
(`cache/effects/`). The navmesh, collision, NPC and verification folders under
`work/cache` are debug outputs of report examples; the viewer does not read them.

Total of that run: about 31 minutes (12 compiling), ~21 GB on disk. A second
`./install.sh` did nothing and took 0.1 s. Index files that the exporters write are kept
in `work/install-state/indexes/`; the committed tables in `data/` are never overwritten.

## Verified

- **The whole flow ran end to end** on the real dumps into the throw-away folder (run 1
  built and extracted the sections, was stopped by hand during `romfs` because it was too
  slow, see below; run 2 resumed with the remembered paths and finished every step; exit 0).
- **The rebuilt data folder is byte-identical to the maintainer's existing extraction:**
  file table 19,095 files / 6,420,119,516 bytes (listing SHA-256 pinned) and a digest over
  every file's path, size and SHA-256 equal to the one computed from
  `work/pla/pk2/romfs_patched` (pinned in the installer, checked on every install).
  `main.nso` and `main.elf` match their pinned SHA-256.
- **Caches match what the viewer expects:** 626/626 field models, 354/354 Pokémon packs
  and 11,765/11,765 audio files that the committed indexes list as exported are present;
  the generated indexes equal the committed `field_model_export_index.tsv`,
  `pokemon_model_export_index.tsv` and `audio_index.tsv` in their source/name/status
  columns (0 differing rows).
- **Byte comparison with the maintainer's caches:** `gltf_field` 1,890/1,890 files,
  `player` 48/48, `terrain_normals` 14/14 identical; `pokemon_batch` 4,393/4,471 identical
  (the other 78 are 33 glTF + 33 bin files of a few packs and 12 `.status` files; that
  cache was rewritten by other work earlier the same day, cause not investigated).
  `terrain_albedo` and `minimap` differ because the maintainer's areas 0 and 2-6 are older
  2048-pixel bakes and the installer bakes 4096 pixels (the size `play.sh` re-bakes with).
- **Idempotent and resumable:** the third run printed every step as `done` and did
  nothing; run 2 removed the one half-written file left by the killed run 1 and skipped
  the files already extracted. `--prune-sections` deleted the 6.4 GB base section and the
  next `--check` still reported everything done (exit 0).
- **Clear errors:** 16 shell checks (`.tools/tests/test_install_sh.sh`) and 44 Python unit
  tests (`test_setup_cache.py`, `test_safe_io.py`) pass: missing, wrong-size, swapped,
  wrong-hash and `.xci` inputs, keys without `header_key`, unknown steps, bad areas, a real
  run that refuses bad inputs before any step (and does not remember them), `--check`
  writing nothing, the pre-flight messages, the dependency order, stale detection when a
  tool source or a parameter changes, and that a write never goes through a symlink.
- **Nothing game-derived is tracked:** `git ls-files` has no containers, executables,
  keys or `work/` paths, and `work/cache`, `work/install-state` are ignored.

## Probable

- The first `romfs` attempt ran below 1 MB/s because every file was synced to disk one by
  one (IO pressure ~55 %); after removing the per-file sync the remaining 17,000 files
  took 1.7 min. A clean `romfs` run from zero is therefore expected around 2-3 minutes on
  this machine, but was not timed from zero.
- The installer works for another user on another machine: the viewer and the cache tools
  get `PLA_BIN_ROOT` / `PLA_CACHE_ROOT` / `PLA_GAME_ROOT` from the installer and `play.sh`,
  so the maintainer's hard-coded default paths are not needed; not tried on a second
  machine or account.

## Assumed

- Staleness of a cache step is decided by the SHA-256 of its example source file plus its
  parameters. Changes in the shared library code (`crates/pla/src`) are **not** detected;
  `--force STEP` rebuilds after such a change.
- Extraction steps are not re-run when only the tool scripts change, because their output
  is checked against pinned hashes.

## Unknown

- Whether `./play.sh` starts and plays correctly from an install made only by the
  installer: the viewer was never opened by the agent (project rule). The maintainer has
  to try `./play.sh --area 1` once.
- Behaviour with other dumps (other revisions, `.nsp`/`.xci`): refused on purpose.
- `--setup-python` (creating `.tools/venv` with `uv`) was not run: the tests used the
  existing venv through `--python`.
- The viewer does not itself detect missing caches; `play.sh`'s pre-flight names them
  with the exact `./install.sh --only …` command instead (to avoid editing the shared
  `port_viewer.rs`).
