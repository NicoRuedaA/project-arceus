# Player dress-up and facial expressions (Brief 36 + Brief 22 expressions)

Code: `crates/pla/examples/player_export.rs` (`--catalog` mode), `assets/player_model.rs`,
`assets/gltf_export.rs` (optional `baseColorFactor`), `game/dressup.rs`,
`game/customize_screen.rs`, `game/face_expr.rs`, `game/player_anim.rs` (multi-scene wiring),
`game/save_game.rs` (v10). Tools/data: `.tools/dressup_catalog.py` →
`data/player_parts_catalog.tsv`; `data/player_parts_index.tsv` (regenerated by the exporter).
Captures (windowless, automation): `work/capturas_personaliz/` (git-ignored).

## The catalogue (VERIFIED)

`chara/table/dressup_table_p{1,2}.bin` decoded with the existing schema-free walk
(`.tools/dressup_table_decode.py`): every row is one catalogue item, its id is
`<variant>_<cat><num>_<NN>_<name>[_<colour>]` and the first four fields are the **stem** (one
mesh pack on disk). `.tools/dressup_catalog.py` groups the rows per stem:

| variant | pieces | slots |
|---|---|---|
| p1 | 66 | hrs 14, face 1, eyb 1, eyew 4, hdw 11, drs 10, tps 5, btm 5, ftw 14, bag 1 |
| p2 | 68 | same, hrs 16 |

Catalogue rows per stem (colour/pattern suffixes) run from 1 (bag) to 81
(`p1_btm0003_00_long`, pattern names like `tartan`, `fire`, `dragon`). The dress-up slots of the
native side (`MyDressup`, `reports/function-progress/n2-weather-dressup-audio.md` §2) map to
these categories one to one (Hair, Eye contacts = the `face` variants, Eyebrow colour, Glasses,
Hat, Tops, Bottoms, Dress, Shoes, Skin tone).

**Clothing colour/pattern variants are NOT rendered.** The rows carry a numeric variant field
(e.g. `p1_btm0003_00_long_fire` → 30, `..._water` → 31, `..._tartan` → 13) and the material uses
`UVIndexLayerMask`/layer masks; how the index selects the texture/layer is **UNKNOWN**, so each
clothing piece is exported with its stem's default textures only.

## Per-piece export (`player_export --catalog`)

One self-contained glTF per stem (134 pieces, all `ok`): `<cache>/player/parts/<variant>/<stem>/
piece.gltf`, each over the shared biped base **plus the canonical extension skeletons the piece
skins to** (face rig 74+, hair 125+, clothes 147+; a piece replaces its own slot's canonical
extension). The eyebrow and some hats carry no `.trskl` of their own and skin to the FACE rig —
exported alone they fail ("active rig outside bind vector"), which is why the canonical set is
merged in. Every piece carries all 17 body clips **and** the 12 real face clips (below). The
merged `<variant>_default/player.gltf` export is unchanged and stays the fallback.

Colour variants baked next to each piece and listed in its `colors.tsv` (`set, name, file`):

| set | count | how |
|---|---|---|
| hair | 15 | grey 32×32 albedo normalised on its mean × ASSUMED RGB (`HAIR_COLOR_PALETTE`, names VERIFIED in `appli/table/hair/hair_color_table.bin`) |
| eyebrow | 15 | same palette, 64×64 |
| eye | 14 | iris-only mask-lerp bake (`save_player_eye_texture_named`), 128×128, names VERIFIED from the `face0001_00_default_<name>` rows |
| skin | 4 | **no PNGs**: skin-bound albedos stay untinted and the glTF `baseColorFactor` carries the tone; the runtime multiplies the material colour. Tones are the VERIFIED sRGB rows of `chara/table/skin_color_table.bin` (two groups of the same four). |

## Runtime

`game/dressup.rs` holds `PlayerLook { variant, hair, hair_color, eyebrow_color, eye_color,
skin_tone, outfit (set | top+bottom), hat, glasses, shoes, bag }`, the embedded catalogue and
`sanitize()` (unknown stems fall back to the variant's defaults, colours/tones are clamped).
The viewer spawns **one scene per worn piece** under `PlayerAvatar` (6–8 scenes), each with its
own `AnimationPlayer`; `player_anim.rs` builds one graph per scene and plays the same clip on all
of them, pinning each scene's `origin` bone. Colour application swaps the base-colour texture
(hair/eyebrow/eye by catalogue name) or multiplies the base colour (skin), handling both the
plain `StandardMaterial` and the `art_style` toon copy. Changing the look respawns the pieces and
re-wires the animation (the customization screen does this live). If `player/parts` is missing,
the merged model (and then the capsule) is used, with a console note.

Save **v10**: the look is a separate `look_` section (11 keys) written by every save path
(F5, Save row, zone autosave) and read back on load; the v9→v10 migration is the documented
no-op arm (a v1–v9 file loads the p1 default look — exactly the model every earlier build
rendered). `PlayerSave::validate` refuses ids with whitespace, `=`, `,` or `|`.

Customization screen (provisional `bevy_ui`, `game/customize_screen.rs`): Esc → **Customize**,
13 rows (protagonist, hair, hair colour, eyebrow colour, eye colour, skin tone, set, top, bottom,
hat, glasses, shoes, bag), Up/Down select, Left/Right/Enter change, Esc back. While it is open the
camera parks in front of the player so the change is visible. The ORIGINAL dress-up layout
(`bin/appli/dressup`, decoded into `work/ui/layouts/dressup.json`: `dressup_00` list + tab part,
`dressup_list_button_00` rows, `dressup_tab_00`) is available but **not bound yet**; the same
look model and catalogue drive it when it is.

## Facial expressions (Brief 22, expressions part)

`pc/dressup_motion.gfpak` holds **real face clips** for the player's face rig
(`00011..00021_faceNN_loop` → `face_01..face_11`, `00201_eye_close01` → `eye_close`; 10 frames @
60 fps, 31–41 tracks of eyelids/eyebrows/lips/jaw/eyeballs). The directory state was recovered by
inverting six known name hashes (`DRESSUP_MOTION_STATE`); the pack contains a second, smaller copy
of the same names (NPC face rig: no eyeball/upper-eyelid tracks) which is NOT used. The helper
tracks `chara_root_exp` and `head_dummy` name no skeleton bone and are dropped.

Measured per clip (deltas from the rest pose, VERIFIED): `face_01 = face_02 = face_03`
(identical, near-neutral), `face_04` eyes shut 24/35/31 mm + jaw 18°, `face_05` brows up 13° +
mouth slightly open, `face_06` brows down 10–11°, `face_07` jaw open 9/16° + mouth corners out
14 mm, `face_08` brows up 20°, `face_09` mouth corners 6 mm only, `face_10` eyes half closed,
`face_11` eyes fully closed (same pose as `eye_close`). The game's own name→clip mapping is NOT in
the extracted data (the controller maps `faceNN` to the `mouth_shape/mouthNN` states, no
expression names), so the mapping in `game/face_expr.rs` is classified from those movements and
labelled per row (normal PROBABLE, serious PROBABLE, anger PROBABLE, damage/smile/rejoice/trouble/
sad SUPUESTO; unique1/unique2 reuse the identical face_02/03 poses). Expressions are played on the
face piece's `AnimationPlayer` (face clips write only face bones, which no body clip touches).
Triggers use decoded mappings: hidden → `face_hide` → serious; battle won/lost →
`face_battle_result_win` → rejoice / `..._lose` → trouble with the decoded keep frames
(90/120 frames of an assumed 30 Hz tick). `--face <name>` forces one for captures. The existing
blink (mesh hide, Brief 22) is unchanged; `eye_close` is the real blink pose if it is ever wired.
